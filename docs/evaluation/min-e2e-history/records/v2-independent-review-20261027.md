## 우선 보완할 사항

### 1. D26/D28은 결과로 연산 순서를 구별할 수 없다

D26과 D28（원문 상대 경로: `v2/질의와_정답_60문항.md`）은 각각 다음을 요구한다.

- D26: B의 전월차를 먼저 구한 뒤 3개월 평균.
- D28: B의 3개월 평균을 먼저 구한 뒤 전월차.

현재처럼 완전한 월별 입력·동일한 구간·같은 단순평균이면 둘 다 `(B(t)-B(t-3))/3`으로 정리된다. 독립 계산에서도 4~6월 결과가 모두 `-0.096666667, -0.086666667, -0.100000000`으로 일치했다. 이는 우연히 고른 숫자가 같아서 생긴 문제가 아니다.

따라서 최종 숫자만 채점하면 두 연산 순서를 잘못 바꿔도 구분하지 못한다. 둘 중 하나를 D32/D33처럼 순서에 따라 값이 달라지는 조합으로 교체하거나, 서로 다른 문장으로 같은 수학적 의미를 이해하는 일관성 문항으로 목적을 바꾸는 것을 권한다.

추가로 D37/D38은 재지수화 후 상대 증감률이므로 기준값 배율이 소거된다. 원계열의 상대 증감률과 최종 숫자가 같다. 이것도 숫자가 틀렸다는 뜻은 아니다. 재지수화 단계를 실제로 거쳤는지를 평가하려면 중간값·근거를 별도로 확인해야 한다.

v1 상세 명세는 같은 수학적 의미의 다른 계산 경로를 허용한다. v2도 이를 이어받고, 계산 경로의 정확한 모양과 수학적으로 동등한 결과를 어떤 기준으로 채점할지 명시하는 편이 좋다. 중간 과정 자체를 요구하는 문항은 그 과정의 관측 항목을 따로 정의한다.

### 2. 다단계 질문은 실행용 steps와 단계별 정답으로 분리하는 것이 좋다

v1은 각 단계의 실행 방식과 정답 변경 상태를 개별적으로 기술한다. v2의 E/F는 questions.jsonl（원문 상대 경로: `v2/questions.jsonl`）의 한 query 문자열 안에 자연어·UI 선택·undo·다운로드 지시를 모두 넣었고, cases.json도 전체 문자열 정답을 저장한다.

사람이 공통 규칙에 따라 한 단계씩 실행하는 용도로는 사용할 수 있다. 자동 평가에서는 전체 문자열을 한 번에 채팅에 보내면 계약이 달라진다. 특히 E33에서 2단계의 구체적 계열·기간·스타일까지 처음부터 모델에 보여주면 1단계의 확인 질문 필요성을 제대로 평가할 수 없다.

`steps` 배열에 `natural_language_edit`, `ui_select`, `ui_undo`, `ui_download` 등의 실행 유형을 구분하고, 각 단계의 기대 변경 상태·보존 상태·파일 revision을 두는 것을 권한다. 문항 통과율과 함께 단계 통과율·실패 단계도 기록하면 단계 수 증가로 인한 실패와 특정 해석 오류를 구분하기 쉽다.

### 3. 준비 검증 통과와 실제 계획·UI 성공을 계속 구분해야 한다

verify.py（원문 상대 경로: `v2/verify.py`）는 cases.json에 작성된 정답 plan을 직접 검증하고 실행한다. 자연어를 받아 제품이 그 계획을 생성하는지, E/F 40문항의 UI 편집·파일이 맞는지는 실행하지 않는다. 각 파생 문항에는 history 검사가 있지만 엔진에는 문항별 조회 범위와 관계없이 전체 1~6월 fixture를 공급한다.

따라서 실제 조회가 필요한 앞달을 확보하는지까지 보려면, 공급 경계의 요청 기간 기록과 문항별 원자료 제공 범위를 별도로 확인해야 한다. 첨부 문서는 준비 검증이고 UI 성공률이 아님을 이미 명시했다. 이 구분은 적절하다. 실제 평가 결과를 발표할 때도 그대로 유지해야 한다.

## 그 밖의 권고

- **E33의 질문 범위:** 계열·범위 확인은 필요하다. 강조 방법까지 반드시 물어야 하는지는 제품의 기본 스타일 정책에 맞춰 명확히 하자. 기본 강조 방식 사용을 허용한다면 이를 사용한 정상 응답을 오답으로 만들면 안 된다.
- **v1과 함께 운영:** v1의 D18 후속 계산 방향 변경과 D20 중간 월 결측은 v2의 단일 턴·완전한 fixture 문항으로 대체되지 않는다. 원본이 밝힌 추가 평가셋이라는 목적대로 v1 회귀와 v2 확장을 함께 유지하는 것이 좋다.
- **검증기 보강:** 현재 verify.py는 Markdown의 문항 수·ID만 확인한다. 지금 실제 질문·정답의 불일치는 없었지만, 추후 수정에 대비해 JSON과 Markdown 질문·정답 문자열 일치도 검사하는 편이 안전하다.
- **다양성 해석:** 동일한 두 금리·여섯 달만 사용하는 것은 변수를 통제하는 데 유용하다. 이 결과로 다른 지표·주기·결측·단위에 대한 일반화 성능까지 주장하지 않는다.

## 권장 사용 방식

v1은 기존 기능 회귀, v2는 복합 편집·파일 상태·계산 조합에 대한 추가 스트레스 평가로 사용한다. 우선 D26/D28의 평가 의도를 정리하고 E/F의 단계별 실행·판정 명세를 보완한 다음 실제 UI 파일럿을 진행하면, 일관되게 채점할 수 있는 추가 평가셋으로 사용할 수 있다.

검토 증거는 독립 검사 결과（원문 상대 경로: `independent-summary.json`）와 검산 스크립트（원문 상대 경로: `independent_check.py`）에 보관했다. 첨부 원본 파일은 수정하지 않았다.
