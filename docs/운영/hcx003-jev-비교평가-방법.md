# StatBridge HCX-003 vs Jev 비교평가 방법 및 데이터 설명서

> **목적**
> 이 문서는 감독관·심사위원·팀원이 “HCX-003과 Jev를 어떤 데이터로, 어떤 조건에서, 어떤 기준으로 비교했는가?”라고 질문했을 때 평가 과정을 재현 가능하게 설명하기 위한 문서입니다.

---

## 1. 한눈에 보는 평가 개요

이번 평가는 일반적인 챗봇 성능을 비교한 것이 아닙니다.

**StatBridge에서 HCX-003이 실제로 담당하는 역할을 기준으로, HCX-003과 Jev가 그 역할을 얼마나 정확하고 안정적으로 수행하는지 비교했습니다.**

평가 대상 모델은 다음과 같습니다.

| 구분 | 모델 | 평가 목적 |
|---|---|---|
| 기존 모델 | HCX-003 | 현재 StatBridge의 통계질문 구조화 모델 |
| 비교 모델 1 | jev-latest | 현재 TypeSafe Jev 안정 버전 |
| 비교 모델 2 | jev-preview | 차기 Jev 후보 모델 |

최종 평가 규모는 다음과 같습니다.

| 항목 | 값 |
|---|---:|
| Gold Set 문항 수 | 100문항 |
| 모델별 반복 실행 | 각 문항 3회 |
| 모델별 총 실행 수 | 300회 |
| HCX-003 총 실행 | 300회 |
| jev-latest 총 실행 | 300회 |
| jev-preview 총 실행 | 300회 |
| 최종 비교에 사용된 총 실행 | 900회 |

## 2. StatBridge에서 HCX-003이 실제로 하는 역할

StatBridge 실제 코드의 `NcpClovaClient.classify_stat_language()`를 기준으로 확인했습니다.

HCX-003은 사용자의 자연어 질문을 받아 **통계 검색에 사용하기 쉬운 구조로 정리**합니다.

예를 들어 사용자가 다음과 같이 질문했다고 가정합니다.

```text
최근 5년 동안 기준금리와 대출금리를 비교해줘
```

HCX-003은 다음과 같은 정보를 만들어냅니다.

```json
{
  "normalized_query": "최근 5년 기준금리 대출금리 추이 비교",
  "concepts": ["기준금리", "대출금리"],
  "subjects": [],
  "measures": ["금리"],
  "time_terms": ["최근 5년"],
  "comparison_terms": ["추이", "비교"],
  "qualifiers": [],
  "series": [
    {
      "label": "기준금리",
      "query": "한국은행 기준금리"
    },
    {
      "label": "대출금리",
      "query": "예금은행 대출금리"
    }
  ]
}
```

즉 HCX-003의 실제 역할은 다음 5가지로 정리했습니다.

1. **질문의 통계 분야를 파악**
2. **추이·비교·비중 등 사용자의 분석 의도를 파악**
3. **계절조정·원계열·말잔·신규취급액 등 세부 조건을 파악**
4. **월별·분기별·연간 등 명시된 자료 주기를 파악**
5. **질문에 여러 독립 통계 지표가 포함된 경우 검색 단위로 분리**

반대로 아래 기능은 HCX-003의 역할이 아니므로 이번 핵심 평가에서 제외했습니다.

- 실제 KOSIS/BOK `table_id`를 임의 생성하는 기능
- `itmId`, `objL1~objL8` 등 실제 API 코드를 생성하는 기능
- 사용자에게 보여줄 역질문 문장을 생성하는 기능
- 최종 통계 결과를 자연어로 설명하는 기능

실제 API 식별자는 StatBridge의 통계언어 사전, 메타데이터, 검색·재정렬 단계에서 검증된 값으로 확정됩니다.

## 3. 왜 일반 벤치마크 대신 StatBridge 전용 Gold Set을 사용했는가

JevBench 같은 공개 벤치마크는 모델의 일반적인 판단 능력을 비교하는 데 유용합니다.

하지만 이번 평가의 핵심 질문은 다음과 달랐습니다.

> **“Jev가 일반적으로 더 좋은 모델인가?”**

가 아니라,

> **“현재 StatBridge에서 HCX-003이 맡고 있는 실제 역할을 Jev가 더 잘 수행할 수 있는가?”**

였습니다.

따라서 StatBridge 실제 데이터 구조와 실제 검색 흐름에 맞춘 별도의 **역할 맞춤 Gold Set**을 구성했습니다.

---

## 4. Gold Set의 출처

Gold Set은 임의의 일반상식 질문 100개를 새로 만들어 사용한 것이 아닙니다.

StatBridge 프로젝트의 실제 `stat_language_dictionary.json` 안에 존재하는 **routing example 29건**을 평가 데이터의 기준으로 사용했습니다.

각 routing example에는 다음과 같은 실제 StatBridge 정보가 들어 있습니다.

- 사용자 질문 예시
- 기대되는 통계표 ID
- 기대되는 분석 의도
- 기대되는 세부 조건
- 해당 통계표의 실제 통계 분야(domain)

Gold Set 생성 시 사용한 주요 근거는 다음과 같습니다.

| 근거 데이터 | 평가에 사용한 정보 |
|---|---|
| `stat_language_dictionary.json` | 실제 통계 분야, routing example, 통계표 정보 |
| routing examples 29건 | 실제 사용자 질문 형태와 기대 통계표 |
| `expected_table_id` | 질문이 어떤 실제 통계표와 연결되어야 하는지 검증 |
| `intent` | 추이·최신·비교·비중 등의 정답 |
| `qualifiers` | 계절조정·말잔·신규취급액 등의 정답 |
| 실제 table `domains` | 통계 분야 정답 |

평가 패키지의 manifest에는 원본 사전과 코드의 SHA-256도 기록했습니다.

```json
{
  "dictionary_sha256": "f0913fd626f9e685cd4371bedc200ecfd86e5c03206d214a6ad2601c9923bb3d",
  "ncp_client_sha256": "665b6fbe7c53b88b79cc3877a9cfd1ff4b6f484bfbd8e4a5451a7f52bbf1cd5b",
  "routing_examples": 29,
  "gold_cases": 100
}
```

이 값은 어떤 버전의 사전과 HCX 클라이언트 코드를 기반으로 평가셋을 만들었는지 추적하기 위한 것입니다.

## 5. 100문항 Gold Set 구성

총 100문항은 다음과 같이 구성했습니다.

| 유형 | 문항 수 | 목적 |
|---|---:|---|
| 단일 통계지표 질문 | 87 | 일반적인 통계 질문 이해 능력 평가 |
| 여러 통계지표가 포함된 질문 | 13 | 독립 검색 지표 분리 능력 평가 |
| **합계** | **100** | |

### 5.1 단일 지표 87문항

StatBridge의 실제 routing example 29건을 기준으로 **의미는 유지하면서 표현만 3종으로 변형**했습니다.

예:

```text
원본: 최근 경제심리지수 추이 보여줘
변형 1: 최근 경제심리지수 추이 보여줘
변형 2: 최근 경제심리지수 흐름 보여줘
변형 3: 최근 경제심리지수 추이 보여줘 통계로 보고 싶어
```

세 문장은 표현은 조금 다르지만 동일한 통계 요구를 의미합니다.

이 방법을 사용한 이유는 모델이 특정 문장 하나를 외우듯 처리하는 것이 아니라 **표현이 달라져도 같은 통계 요구를 이해하는지** 확인하기 위해서입니다.

### 5.2 다중 지표 13문항

HCX-003의 실제 프롬프트에는 다음 규칙이 있습니다.

> 비교할 지표가 2~5개이면 `series`에 각각 독립적으로 검색 가능한 통계 지표를 넣고, 단일 지표면 `series`는 빈 배열로 둔다.

따라서 이 기능을 별도로 검증하기 위해 다중 지표 문항을 추가했습니다.

다중 지표 Gold의 구성은 다음과 같습니다.

| 정답 검색 지표 수 | 문항 수 |
|---|---:|
| 단일 지표, 분리 불필요 (`0`) | 87 |
| 2개 독립 지표 | 11 |
| 3개 독립 지표 | 2 |

## 6. Gold Set이 포함하는 통계 분야

100문항은 특정 한 종류의 통계에만 집중하지 않았습니다.

실제 Gold Set에 포함된 주요 통계 분야 예시는 다음과 같습니다.

- 예금·대출
- 소비자심리
- 무역·환율
- 물가·무역가격
- 경제심리
- 지급결제
- 기업경기
- 통화·유동성
- 금리
- 국민계정
- 국제수지
- 기업금융
- 생산자물가
- 대출행태

즉 “금리 질문만 잘 맞히는가?” 같은 단일 분야 테스트가 아니라, StatBridge가 실제로 다루는 여러 통계 영역에 걸쳐 평가했습니다.

## 7. Gold Set 한 문항의 구조

각 문항은 단순 질문 문자열만 갖는 것이 아니라, 자동 채점에 필요한 정답 정보를 함께 갖습니다.

실제 구조 예시는 다음과 같습니다.

```json
{
  "case_id": "R01-V1",
  "kind": "single_metric",
  "query": "최근 경제심리지수 추이 보여줘",
  "source_query": "최근 경제심리지수 추이 보여줘",
  "expected_table_id": "DT_513Y001",
  "expected_table_name": "경제심리지수",
  "expected_domains": ["economic_sentiment"],
  "expected_intents": ["trend", "latest"],
  "expected_qualifiers": [],
  "expected_frequency": null,
  "expected_series_count": 0,
  "dimension_hints": ["경제심리지수(원계열)"]
}
```

각 필드의 의미는 다음과 같습니다.

| Gold 필드 | 의미 |
|---|---|
| `case_id` | 문항의 고유 ID |
| `kind` | 단일 지표 / 다중 지표 구분 |
| `query` | 실제 모델에 입력하는 사용자 질문 |
| `source_query` | 변형 문장을 만들기 전 기준 질문 |
| `expected_table_id` | 원래 routing example의 기대 통계표 |
| `expected_table_name` | 기대되는 실제 통계표 이름 |
| `expected_domains` | 질문의 통계 분야 정답 |
| `expected_intents` | 추이·최신·비교·비중 등의 정답 |
| `expected_qualifiers` | 계절조정·말잔·신규취급액 등의 조건 정답 |
| `expected_frequency` | 월별·분기별·연간 등 명시 주기 |
| `expected_series_count` | 몇 개의 독립 검색으로 나누어야 하는지 |
| `dimension_hints` | 실제 통계표의 관련 분류값 참고 정보 |

## 8. HCX-003 평가 방법

HCX-003은 **실제 StatBridge에서 사용하는 역할과 최대한 동일한 방식**으로 평가했습니다.

평가 시 프롬프트는 평가 도중 바꾸지 않도록 별도 파일에 고정했습니다.

주요 시스템 지시는 다음과 같습니다.

```text
너는 StatBridge 통계언어 분류기다.
사용자의 일상 자연어를 통계 검색에 필요한 표현으로만 정규화한다.
통계표 ID, itmId, objL 코드, 숫자 데이터는 절대 추측하지 마라.
반드시 JSON 객체 하나만 출력한다.
```

주요 생성 파라미터도 고정했습니다.

| 설정 | 값 |
|---|---:|
| temperature | 0.01 |
| topP | 0.1 |
| topK | 0 |
| repetitionPenalty | 1.05 |
| maxTokens | 700 |

HCX-003의 JSON 결과를 평가기가 공통 정답 형태로 변환한 뒤 Gold Set과 비교했습니다.

## 9. Jev 평가 방법

Jev는 HCX-003처럼 자유로운 JSON 문장을 생성하는 일반 생성형 인터페이스가 아닙니다.

Jev는 **미리 주어진 후보에서 선택하거나 Yes/No 확률을 반환하는 판단형 모델**이므로, HCX와 완전히 같은 출력문장을 생성시키는 것은 오히려 불공정합니다.

따라서 Jev에는 **동일한 사용자 질문**을 주고, Gold Set에서 비교하려는 항목을 선택형 질문으로 변환했습니다.

예를 들어 통계 분야 판단은 다음과 같은 방식입니다.

```text
사용자 질문:
최근 경제심리지수 추이 보여줘

후보:
- 경제심리
- 소비자심리
- 금리
- 예금·대출
- 통화·유동성
...
```

Jev는 이 후보 중 하나를 선택합니다.

추이·비교·비중 같은 분석 의도와 세부 조건은 각각 Yes/No 판단으로 측정했습니다.

즉 두 모델의 API 출력 형식은 다르지만, 최종적으로는 동일한 canonical 항목으로 변환했습니다.

```text
통계 분야
분석 의도
세부 조건
자료 주기
독립 검색 지표 수
```

그리고 이 canonical 결과를 **동일한 Gold 정답과 비교**했습니다.

## 10. “같은 조건”의 의미

이번 평가에서 “같은 조건”이라는 말은 **API 문법까지 똑같이 만들었다는 뜻이 아닙니다.**

HCX와 Jev는 본래 인터페이스가 다르기 때문입니다.

같게 통제한 것은 다음입니다.

1. **동일한 100개 사용자 질문**
2. **동일한 Gold 정답**
3. **동일한 평가 항목**
4. **동일한 채점 계산**
5. **각 문항 3회 반복**
6. **동일한 실행 PC와 평가 프로그램**
7. 모델별 고유 출력은 공통 canonical 구조로 변환 후 비교

이 방식은 모델별 API 특성은 유지하면서 **StatBridge에서 필요한 실제 업무 결과를 같은 기준으로 비교**하기 위한 것입니다.

## 11. 측정 항목과 뜻

AI를 모르는 사람도 이해할 수 있도록 각 지표를 아래와 같이 정의했습니다.

| 측정 항목 | 쉽게 설명하면 | 계산 방법 |
|---|---|---|
| 통계 분야 파악 정확도 | 질문이 금리인지, 물가인지, 고용인지 제대로 알아내는가 | 정답 분야를 맞힌 횟수 / 전체 |
| 분석 의도 F1 | “추이”, “비교”, “비중”, “최신” 같은 요구를 빠뜨리거나 잘못 추가하지 않는가 | 의도별 Precision·Recall의 조화평균 |
| 세부 조건 F1 | “계절조정”, “말잔”, “신규취급액” 같은 조건을 제대로 찾는가 | 조건별 Precision·Recall의 조화평균 |
| 자료 주기 정확도 | 명시된 월별·분기별·연간을 맞히는가 | 주기 정답 문항 중 맞힌 비율 |
| 다중 지표 분리 정확도 | 한 질문을 몇 개의 독립 통계검색으로 나눠야 하는지 맞히는가 | 정답 지표 수를 맞힌 비율 |
| 정상 출력률 | 프로그램이 실제로 해석 가능한 정상 응답인가 | HTTP 200 + 해석 가능한 출력 비율 |
| 반복 일관성 | 같은 질문을 세 번 했을 때 판단이 계속 같은가 | 3회 결과가 완전히 동일한 문항 비율 |
| p50 응답시간 | 일반적인 요청은 얼마나 빨리 끝나는가 | 응답시간 중앙값 |
| p95 응답시간 | 느린 요청까지 포함하면 어느 정도 걸리는가 | 응답시간 95백분위 |
| API 오류율 | 모델 호출 자체가 실패하는가 | HTTP 오류 / 전체 요청 |

## 12. 역할 종합점수 계산 방법

`role_score`는 한 문항에서 다음 요소를 동일 비중으로 평균했습니다.

기본적으로:

```text
통계 분야 정답 여부
+ 분석 의도 F1
+ 세부 조건 F1
+ 다중 지표 분리 정답 여부
```

질문에 자료 주기가 명시된 경우에는 다음 항목을 추가했습니다.

```text
+ 자료 주기 정답 여부
```

즉 주기가 없는 문항은 4개 요소 평균, 주기가 명시된 문항은 5개 요소 평균입니다.

그 후 전체 300회 실행의 평균을 백분율로 환산해 `role_score_pct`를 만들었습니다.

### 중요한 주의점

이 종합점수는 StatBridge 역할 비교를 편하게 보기 위한 **내부 요약 지표**입니다.

특정 모델의 일반적인 AI 지능이나 전체 능력을 의미하지 않습니다.

특히 이번 실험에서는 `다중 지표 분리 정확도`에서 모델 간 차이가 매우 커서 종합점수 차이에도 큰 영향을 주었습니다.

따라서 최종 의사결정에서는 종합점수 하나만 보지 않고 **세부 항목을 함께 확인했습니다.**

## 13. 왜 각 문항을 3번 반복했는가

AI 모델은 같은 질문에도 실행마다 결과가 조금 달라질 수 있습니다.

한 번만 실행하면 우연히 맞거나 틀린 결과가 전체 평가에 영향을 줄 수 있기 때문에 모든 문항을 3회 반복했습니다.

100문항 × 3회 = 모델당 300회입니다.

또한 세 번의 핵심 판단이 완전히 같았는지를 별도 `consistency` 지표로 기록했습니다.

따라서 정확도뿐 아니라 **서비스에서 반복 사용했을 때 판단이 흔들리는지도 확인**했습니다.

## 14. Jev 최초 실패 결과를 최종 비교에서 제외한 이유

첫 Jev 실행에서는 Jev API의 `choice` 요청 형식을 잘못 구성했습니다.

당시 요청은 `options` 필드를 사용했지만, 실제 API는 `criteria` 구조를 요구했고 Jev 요청 전체가 HTTP 422로 실패했습니다.

이 실행은 모델의 성능 실패가 아니라 **평가 프로그램의 API 스키마 오류**였기 때문에 최종 성능 비교에서 제외했습니다.

HCX-003의 기존 300회 정상 평가 결과는 그대로 보존했고, Jev 요청 부분만 수정해 동일 Gold Set으로 다시 평가했습니다.

재평가 결과:

- `jev-latest`: 300회 중 299회 HTTP 200
- `jev-preview`: 300회 중 300회 HTTP 200

따라서 최종 비교에는 **정상 Jev 재평가 결과만 사용**했습니다.

이 과정에서 HCX-003 결과를 다시 돌리거나 좋은 결과만 선택하지 않았습니다.

## 16. 결과를 어떻게 해석했는가

이번 평가에서 HCX-003은 다음 항목에서 강했습니다.

- 통계 분야 파악: 98%
- 분석 의도 파악: 64.23%, Jev보다 높음
- 세부 조건 추출: 93.33%
- 자료 주기 판단: 100%
- 3회 반복 일관성: 100%

반면 HCX-003의 가장 큰 약점은 **다중 지표 분리 판단**이었습니다.

```text

jev-latest   95.67%
jev-preview  96.33%
```

따라서 최종 설계 방향은 HCX-003 전체를 Jev로 교체하는 방식이 아니라,

> **HCX-003은 기존 자연어 이해·통계 구조화 역할을 유지하고, 다중 지표 분리 판단만 Jev를 추가로 사용하는 하이브리드 방식**

## 17. 왜 HCX-003 전체를 Jev로 교체하지 않았는가

Jev의 종합점수는 HCX-003보다 높았지만, 세부 항목을 보면 Jev가 모든 부분에서 우수한 것은 아니었습니다.

예를 들어:

```text
통계 분야 파악
HCX-003: 98.00%
Jev Preview: 91.33%

분석 의도 파악
HCX-003: 64.23%
Jev Preview: 60.43%
```

즉 현재 HCX-003이 잘 수행하는 자연어 이해 부분까지 굳이 교체할 근거는 부족합니다.

반대로 다중 지표 분리에서는:

```text
HCX-003: 28.00%
Jev Preview: 96.33%
```

으로 차이가 매우 컸습니다.

따라서 **실측에서 실제로 약점이 확인된 기능만 Jev로 보완하는 것**이 가장 작은 변경으로 가장 큰 효과를 얻는 방법이라고 판단했습니다.

## 18. 평가의 한계

감독관 관점에서 반드시 같이 밝혀야 할 한계는 다음과 같습니다.

### 18.1 100문항은 StatBridge 전용 데이터다

이번 결과는 일반적인 AI 능력 전체를 의미하지 않습니다.

StatBridge의 통계 검색·구조화 역할에 한정된 평가입니다.

### 18.2 87문항은 29개 기준 질문에서 파생됐다

표현 다양성을 보기 위해 29개 실제 routing example을 3종으로 변형했습니다.

따라서 완전히 독립적인 87개의 서로 다른 업무 시나리오라고 보기는 어렵습니다.

향후 최종 검증에서는 기존 29개와 겹치지 않는 **별도 Holdout 질문**을 추가하는 것이 좋습니다.

### 18.3 다중 지표 문항은 13개다

Jev와 HCX의 가장 큰 차이가 나온 다중 지표 분리는 13개 문항을 중심으로 검증되었습니다.

3회 반복으로 총 39회 판단을 확인했지만, 실제 서비스 적용 전에는 다중 지표 문항을 더 확대하는 것이 좋습니다.

### 18.4 HCX와 Jev의 출력 방식은 다르다

HCX는 자연어 기반 JSON을 생성하고, Jev는 후보 기반 판단을 수행합니다.

따라서 “완전히 같은 API 출력 능력” 비교가 아니라,

**서로 다른 모델이 같은 StatBridge 업무 정답을 얼마나 잘 만들어내는지** 비교한 것입니다.

### 18.5 속도는 이번 실행 환경 기준이다

p50/p95는 같은 평가 PC에서 측정했지만 각 서비스의 서버 위치, 네트워크 상태, API 내부 부하에 따라 달라질 수 있습니다.

따라서 고정된 절대 성능 보장값보다는 **이번 실험에서 관측된 실측값**으로 해석해야 합니다.

## 20. 감독관 질문에 대한 짧은 답변 예시

### Q. 어떤 데이터로 비교했습니까?

StatBridge 실제 통계언어 사전의 routing example 29건과 해당 통계표의 실제 domain, intent, qualifier 정보를 기준으로 Gold Set을 만들었습니다. 29개 실제 질문을 의미가 바뀌지 않도록 3종으로 변형해 87문항을 구성했고, 다중 통계지표 분리 능력을 확인하기 위한 13문항을 추가하여 총 100문항으로 평가했습니다.

### Q. 두 모델에 같은 시험을 준 것이 맞습니까?

네. 두 모델 모두 동일한 100개 사용자 질문과 동일한 Gold 정답으로 평가했습니다. 단, HCX와 Jev의 API 특성이 다르기 때문에 출력 문법 자체를 억지로 같게 만들지는 않았습니다. HCX는 실제 StatBridge JSON 구조화 방식으로 실행했고, Jev는 같은 질문에서 동일 평가 항목을 선택형/Yes-No 방식으로 판단한 뒤 공통 구조로 변환해 같은 정답과 비교했습니다.

### Q. 한 번씩만 실행한 것입니까?

아닙니다. 모델별로 100문항을 각각 3회 반복하여 총 300회씩 실행했습니다. 세 번의 판단이 계속 같은지도 별도의 반복 일관성 지표로 측정했습니다.

### Q. 무엇을 점수로 비교했습니까?

통계 분야 파악, 사용자의 분석 의도 파악, 세부 조건 추출, 월·분기·연간 주기 판단, 여러 지표를 몇 개의 독립 검색으로 분리할지 판단하는 능력을 비교했습니다. 정상 출력률, 반복 일관성, API 오류율, 응답속도도 함께 측정했습니다.

### Q. Jev가 종합점수가 높으니 HCX를 전부 바꾸는 겁니까?

아닙니다. 세부 결과를 보면 HCX-003은 통계 분야 파악과 자연어 의도 이해에서 Jev보다 높았습니다. Jev가 크게 앞선 부분은 다중 지표 분리 판단이었습니다. 따라서 HCX-003의 기존 역할을 유지하면서 다중 지표 분리 판단에만 Jev를 사용하는 하이브리드 구조를 우선 검토하고 있습니다.

### Q. 평가 중 실패한 Jev 결과도 포함했습니까?

아닙니다. 최초 Jev 실행은 평가 프로그램에서 API 요청 필드를 잘못 사용하여 HTTP 422가 발생한 테스트였고, 모델 성능 평가로 볼 수 없어서 제외했습니다. HCX 결과는 그대로 보존하고 Jev 요청 형식만 수정한 뒤 같은 100문항으로 다시 평가했습니다. 최종 수치는 정상 재평가 결과입니다.

## 21. 최종 요약

이번 비교평가는 다음 원칙으로 수행했습니다.

```text
실제 StatBridge 역할을 먼저 확인
        ↓
실제 StatBridge 사전 기반 Gold Set 100문항 구성
        ↓
HCX-003 / Jev에 동일 질문 제공
        ↓
모델별 고유 출력방식을 공통 평가항목으로 변환
        ↓
같은 Gold 정답으로 자동 채점
        ↓
각 문항 3회 반복
        ↓
정확도 + 안정성 + 속도 + 오류율 비교
```

따라서 이번 평가는 단순히 공개 벤치마크 숫자를 가져와 비교한 것이 아니라,

**StatBridge에서 실제로 필요한 업무를 기준으로 HCX-003과 Jev를 동일 Gold Set에서 직접 실행하여 비교한 역할 맞춤 평가**입니다.

최종 실측에서는 HCX-003이 자연어 기반 통계 분야·의도 이해에서 강점을 보였고, Jev는 다중 지표 분리 판단과 처리 속도에서 큰 강점을 보였습니다. 이 결과를 근거로 HCX-003을 전면 교체하기보다 **다중 지표 분리 판단에 Jev를 보조적으로 사용하는 구조**를 우선 검토하고 있습니다.
